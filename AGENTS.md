# AGENTS.md — Rules of Engagement & Engineering Standards

This document establishes the binding architectural constraints, domain terminology rules, and engineering standards for any developer or AI agent working on the **Predict-Ai (PrediCore)** platform.

---

## 1. Non-Negotiable Product Rules (from PRD v3.0)

1. **C-MAPSS FD001 Domain Integrity**:
   - C-MAPSS FD001 is **simulated turbofan engine degradation data**.
   - **NEVER** refer to it as motor data, pump data, or real plant data.
   - Display sensors **only** by their original identifiers (`sensor_1`...`sensor_21`, `op_setting_1`...`op_setting_3`).
   - **NEVER** invent physical meanings (e.g., temperature, vibration, pressure, "thermal stress").
   - Dashboard banner text must be exactly:  
     `"Demo Dataset: NASA C-MAPSS FD001 — Simulated Turbofan Engine Data"`  
     and demo items must carry a `"Demo / Simulated Data"` badge.

2. **Zero Fabricated Metrics**:
   - Every metric on the Model Performance page must originate from a stored `model_evaluations` record generated by Colab evaluation.
   - **NO metric literals** in frontend, backend, or seed code.
   - If no evaluation record exists, display: `"Model evaluation not available."`

3. **Approved vs Forbidden Terminology**:
   - **Approved**: *Failure Probability* (with horizon $H$), *Prediction Reliability*, *Machine Health Indicator*, *AI recommendation*.
   - **Forbidden in MVP**: *confidence*, *diagnosis*, *health measurement*, *prescription*.

4. **Strict Separation of Training and Inference**:
   - The backend **only** loads registered, checksum-verified model bundles.
   - The backend **never** fits, trains, or retrains models. All ML fitting occurs offline in Colab.

5. **Inflexible Compatibility Gate**:
   - Inference is blocked unless the dataset passes all PRD FR-6 compatibility checks.
   - Incompatible datasets produce: `"This dataset is not compatible with the selected model."` alongside an Expected/Found/How-to-fix table. Scoring returns HTTP `409 Conflict (DATASET_INCOMPATIBLE)`.

6. **Lineage on Every Prediction**:
   - Every prediction must store: machine, dataset version, `schema_mapping_hash`, feature config version, preprocessing version, failure and anomaly model versions, horizon + unit, `as_of_index`, `predicted_at`, `input_window`, and `health_config_id`.
   - UI section: *"How was this prediction generated?"*.

7. **Model Cards Required for Activation**:
   - A model cannot become active without a complete model card and an attached evaluation record (enforced via DB CHECK and service validation).

8. **Demo Mode is Real, Not Faked**:
   - Demo machines are held-out FD001 test engines scored by the real registered model through the normal pipeline.
   - Deterministic selection of Healthy / Warning / Critical machines.

9. **AI vs Human Authority Stays Distinct**:
   - Visually and structurally distinguish:  
     $$\text{AI Prediction} \longrightarrow \text{AI Recommendation} \longrightarrow \text{Engineer Decision \& Action} \longrightarrow \text{Maintenance Outcome}$$
   - Every recommendation must carry:  
     `"AI-generated recommendation, not a confirmed diagnosis. Verify with a qualified engineer."`

10. **Roles & RBAC**:
    - Exactly two roles: `admin` and `engineer`, strictly enforced server-side.

## 2. Engineering Standards & Code Quality

1. **Type Safety & Linters**:
   - Python: Strict typing (`ruff`, `mypy`), Pydantic v2 schemas at the boundaries.
   - TypeScript: Strict mode (`oxlint` / `eslint`), zero unhandled `any` casts without explanatory comments.
   - Return clean JSON error responses: `{"error": {"code": "...", "message": "...", "details": ...}}`. Never leak stack traces to clients.

2. **Database Hygiene (Neon PostgreSQL)**:
   - Use pooled URL (`DATABASE_URL`) with `prepare_threshold=None` for app runtime.
   - Use direct URL (`DATABASE_URL_DIRECT`) for Alembic migrations.
   - Neon scale-to-zero resiliency: `pool_pre_ping=True` and connection retry backoff.
   - Never store training data or raw model weights in the relational database.

3. **Shared ML Core (`pdm_core`)**:
   - All feature engineering, labeling, evaluation metrics, and bundle definitions live in `ml/src/pdm_core`.
   - Used identically in Google Colab and FastAPI inference to prevent training/serving skew.
   - Pure, past-only feature transformations. Unit tests enforce zero future data leakage.

4. **Testing Protocol**:
   - Tests run against throwaway local Postgres (docker-compose) or SQLite/memory where appropriate. Never run tests against development or production Neon data.
   - Static linters in CI ensure no hardcoded numerical metrics or physical sensor mappings exist in source code.
